# Duplicate Servings Report — s3/2026-08-06-approved-foods.json

Generated by `backend/data-prep/find_duplicate_servings.py`. 42 foods have at least one serving name that appears more than once with conflicting values (no byte-identical duplicates found).

## Likely-cause categories

- **DIFFERENT QUANTITY** — the same serving *name* (e.g. "cup") is reused for genuinely different amounts (0.2 cup, 0.5 cup, 1 cup all just called "cup"). Root cause: a serving-name that should carry the amount ("1/4 cup", "1/2 cup") lost that qualifier somewhere in cleanup/collation.
- **PARTIAL EXACT DUPLICATE** — two of the group's entries are byte-identical, plus one that differs. Consistent with a food being re-submitted/re-approved (e.g. after the kcal/kJ conversion-bug fix) without removing its earlier, uncorrected serving of the same name — both ended up in the exported servings list.
- **SAME QUANTITY, DIFFERENT MACROS** — same name, same quantity, but no two entries match at all. Consistent with two distinct USDA source records (e.g. a Foundation Foods entry and a separate FNDDS/Survey entry, or two different Survey revisions) sharing a food name and colliding under the same id (ids are a deterministic hash of the cleaned name), each contributing its own "fl oz"/"regular"/"can or bottle" serving that never got deduplicated because the values genuinely differ.

All but one duplicate food has a **uuid5** id (deterministic hash of the food name, used by the offline USDA data-prep pipeline in `convert_foundation_foods_for_kaios_local.py`/`convert_survey_foods_for_kaios_local.py`) — i.e. these came from the bulk-imported catalog, not from an end user's own submission. The one exception (Shake Shack Chicken Bites Nuggets) has a random **uuid4** id, meaning it was added directly through the admin "Add Food" flow.

### The real finding: these 17 groups aren't "conflicting" data — they're the same food at different (unlabeled) portion sizes

The report's category 3 theorizes two *independent* USDA records colliding on a shared id, each with its own unrelated macros. That's not quite what's happening. I checked every field (calories, carbs, fat, protein, alcohol, caffeine) within each group and **every single group scales by one consistent ratio across all fields**:

A perfectly proportional scaling across every macro (protein, fat, carbs, calories, alcohol *and* caffeine) is the signature of the **same per-gram nutrition profile evaluated at two different portion weights** — not two disagreeing lab records. The alcoholic drinks are the clearest case: 4/3 is exactly the ratio between a 12 fl oz can and a 16 fl oz can/bottle. Same underlying beer, two real can sizes, both ended up labeled "can or bottle".

**Root cause, found in code:** `backend/data-prep/convert_survey_foods_for_kaios_local.py:93`:

```python
{'find': re.compile(r'\s*\([^()]+\)$', re.IGNORECASE), 'replace': ''},
```

This strips any trailing parenthetical off the raw USDA portion description *before* the serving name is derived — e.g. `"1 can or bottle (12 fl oz)"` and `"1 can or bottle (16 fl oz)"` both collapse to `"1 can or bottle"`, losing the only text that distinguished them. The USDA Survey/FNDDS dataset contains multiple portion rows per food (different real-world container/slice/piece sizes); this line throws away the size qualifier for all of them, so any food with more than one size variant produces same-named-but-different-valued servings once collated. Both values are legitimate — they just describe different real quantities of the same food.
